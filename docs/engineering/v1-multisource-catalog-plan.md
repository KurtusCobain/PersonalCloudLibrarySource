# PCLS v1.0 multi-source runtime — coding checkpoint

**Status:** Experimental, default-off draft implementation in [PR #22](https://github.com/KurtusCobain/PersonalCloudLibrarySource/pull/22). **Not approved for use, merge or public release.** Public v0.3.2 remains unchanged. This is not a native Playnite acceptance result.

## What has been coded

- **Stable source identity:** `SourceProfileIdentityPolicy` retains all legacy single-source GameIds, assigns source-namespaced IDs to added profiles, refuses duplicate profile IDs and prevents game-ID collisions.
- **Versioned source settings:** `SourceProfilesConfigurationCodec` serializes/deserializes a bounded version-1 profile document, rejects absent/unsupported schema and malformed IDs, and previews legacy migration without writing live settings.
- **Atomic file storage:** `SourceProfilesFileStore` saves that separate document into a preexisting plugin-owned directory using a unique temporary file, atomic replace/move and a unique backup of the prior valid configuration. It refuses overwriting corrupt/unsupported existing configurations, follows no known reparse-point paths and provides explicit backup **inspection**, not automatic rollback. The store is now called only from an explicit preview-screen Save action; it is never an automatic settings migration.
- **Source-local runtime snapshots:** `SourceProfileSettingsProjector` preserves legacy remote timeout and configuration and produces source-scoped settings without changing active user settings. Outside-cache uninstall permission is refused for multi-source.
- **All-or-nothing catalog planning:** `MultiSourceRuntimeCoordinator` reads independently validated manifests and checks complete mapping, disabled/offline sources and exact/ancestor-overlapping cache destinations before publishing anything. A partial success must not cause Playnite to discard offline games.
- **Source-bound action routing:** `MultiSourceControllerFactory` checks expected Playnite plugin ownership and the matching plan route, then supplies source-specific item/settings copies to install and uninstall controllers. The new-profile install passes its **namespaced** GameId as the receipt key. Legacy receipt keys remain the exact original item ID. This has isolated Windows fixtures with real disposable file transfers.
- **Explicit backup recovery:** the settings preview now lists bounded, filename-validated local profile backups. A selected backup must be inspected as a read-only source list before the Restore button is enabled. The management layer re-checks both the live profile document and the selected backup at commit time. Restore refuses a backup that adds/removes source GUIDs, changes a source's legacy flag, disables a source, is corrupt, or changed since inspection. A successful restore writes through the existing atomic profile store, creating a **new backup of the configuration replaced**. Restoration does not enable multi-source mode or touch game content. **Deliberate limitation:** a corrupt active profile file is not auto-overwritten, even if an older backup is valid; manual recovery remains necessary until reviewed.

- **Read-only per-source manifest health:** the Source Profiles preview now offers an explicit **Check selected manifest** button, off the UI thread. The probe distinguishes valid manifest, unreachable provider, malformed manifest, unsupported schema, disabled profile and invalid configuration without changing Playnite games, cache files, ownership receipts, live settings or source-profile persistence. Remote checks can take up to the configured rclone timeout; a healthy manifest does **not** prove every game payload is reachable. Health results are diagnostic only and must never be interpreted as authorization to retire or remove offline entries.

- **Identity-only offline continuity groundwork:** `SourceCatalogContinuityPolicy` can capture prior *successfully validated* per-source GameIds into an immutable, bounded in-memory inventory bound to a SHA-256 fingerprint of the source identity, manifest configuration and shared cache scope. An unavailable manifest with matching history is classified as an **offline identity candidate**, not as an import success. Missing/empty history, changed source GUID/provider/manifest/cache, disabled profiles, malformed/unsupported data, and incomplete source-to-game mappings refuse replay. Neither `GetGames` nor install/uninstall paths consume the candidate; there is no disk persistence, content snapshot, automatic restore or permission to use stale actions. The strict all-or-nothing import path remains in effect. This slice deliberately stops *before* last-known-good catalog replay.

- **Durable identity-only snapshot store:** `SourceCatalogSnapshotStore` now explicitly saves and reads bounded version-1 identity inventories in the existing plugin-owned directory. Records contain only the source GUID, source-binding fingerprint, mapped GameIds and an SHA-256 integrity checksum. The checksum detects accidental corruption but is **not** a digital signature or protection from a malicious local file editor. Existing valid snapshots are backed up during atomic replacement; corrupt, missing, linked, oversized and unsupported-schema files are rejected rather than silently replaced. The snapshot store has no live runtime caller, stores no launcher actions or uninstall paths, performs no cache cleanup, and cannot publish an offline catalog to Playnite. Concurrent external file replacement/path races remain an independent Windows security-review gate.

- **Quarantined display metadata evidence:** `SourceCatalogDisplaySnapshotStore` now captures a *display-only* subset (source-bound GameId, name, description) from an already complete, validated import. A separate bounded, versioned JSON store preserves those records with checksum validation, atomic replacement and backup. Identity snapshots must agree on exact source GUID, source-binding fingerprint, and game-ID set; changed manifest/cache binding refuses association. The store deliberately excludes `GameActions`, executable/working-directory paths, install state, install size, install directory, ownership receipts and uninstall/delete permissions. It is **not** used by `GetGames`, cannot restore cached files, and cannot mark an offline import successful. It is not yet a full Playnite metadata snapshot. JSON checksums detect accidental corruption, not malicious local edits; external concurrent replacement/link races still require Windows review.

- **Live stale-action quarantine:** experimental `GetInstallActions` and `GetUninstallActions` now re-read the validated source profile document and compare it with a configuration fingerprint stored in the most recent *fully successful* `MultiSourceRuntimePlan`. The fingerprint covers the entire source-profile document plus shared cache scope, download permissions, uninstall policy, missing-file interpretation, transfer concurrency, verification and incomplete-transfer behavior. Changed/disabled/corrupt/unknown profiles invalidate the in-memory route and refuse both actions until a successful refresh. A long-running remote import also checks configuration again before publishing routes, failing closed if settings changed while importing. Display-only UI and notification settings do not unnecessarily invalidate actions. **Limits:** SHA-256 detects drift, not adversarial tampering; this does not guarantee an unchanged underlying manifest or eliminate filesystem replacement races after the final check. Previously constructed controllers are not retroactively cancelled. This is an active experimental-runtime guard, not offline catalog replay.

- **Guarded Playnite integration:** `PersonalCloudLibrarySource.GetGames`, `GetInstallActions` and `GetUninstallActions` now have an experimental path gated by `EnableMultiSourceProfiles`. This setting defaults **false** and is copied correctly through the settings edit/rollback path. Normal single-source imports/actions retain their existing path. The experimental path requires a valid independent profile file; it fails closed with an exception rather than returning a successful partial catalog. Failed preparations invalidate the old action plan.

- **Preview UI:** A new localized "Source Profiles (1.0 Preview)" settings tab lets users load or preview the original source, add local/folder/rclone profiles, edit source-local connection fields and explicitly save. `SourceProfilesManagementService` validates complete profile configurations, preserves the legacy source ID, blocks removal/re-identification/disable, refuses stale edits and does **not** activate the new runtime. There is currently no automatic rollback, source retirement, live source status or built-in 7z/RAR functionality in this tab. Playnite .NET 4.6.2 XAML and localization contracts are covered by CI.

## Verified boundaries

- The legacy settings schema/version remains unchanged until the final v1 migration design and review.
- This branch does not enable a GUI toggle, auto-create a profile file, silently adopt missing sources, or issue delete permissions for game directories.
- No active cloud credentials, real NAS or private game archives are used in the automated fixtures.
- A matching V2 ownership receipt is informational, not authorization for recursive deletion. Cached-file uninstall continues to rely on the original safe deletion policy.

## Outstanding v1.0 release gates

1. **Native Playnite host acceptance:** experimental `GetGames`/action routing, stable IDs during updates, keyboard/Desktop/Fullscreen behavior and source reconnect; currently automated tests cannot establish host parity.
2. **Complete profile-management UX:** localized add/edit/save preview and explicit validated same-identity backup restore are implemented; source disable/retirement, ongoing live monitoring (manual manifest checks only), conflict resolution, coherent Settings Cancel semantics, and corrupt-current recovery still need design and acceptance. A disabled source must not silently remove catalog entries.
3. **Last-known-good snapshots:** bounded persistent identity records and **display-only** metadata evidence are now separate, inactive stores. Exact full Playnite metadata fidelity, provenance freshness, automatic save timing, crash recovery, cross-source cache collision checks and a safe method to suppress stale install/uninstall actions still need design and validation. **No offline replay is enabled**; current strict strategy still fails the entire import on any failed source.
4. **Settings migration and lifecycle:** complete source-profile save/restore, supported upgrade from v0.2.0/v0.3.2 and refusal of corrupt profiles. The default-off experimental bit is not a finished migration or supported user setting.
5. **Filesystem threat review:** path/link races and file-replacement atomicity need independent adversarial Windows review. No directory-delete expansion without a separate safety decision.
6. **Other 1.0 pillars:** ZIP staging to live Install UI, safe 7z/RAR implementations, executable confirmation, size-reporting compatibility, accessibility and diagnostics.
7. **Freeze and review:** consolidate all draft PRs, run full Windows CI on exact integrated SHA, obtain Claude/Grok/Nova independent reviews, fix their blockers, then one consolidated disposable Windows acceptance and explicit owner release authorization.

This branch must remain **draft/unmerged**. CI success proves the automated fixture contract, **not** full multi-source production readiness.
