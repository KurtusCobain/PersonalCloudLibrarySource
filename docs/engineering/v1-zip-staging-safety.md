# PCLS v1 package import: ZIP staging implementation checkpoint

**Status: draft development code, not a shipped or enabled Playnite install mode.** This is a coding-first candidate on [PR #21](https://github.com/KurtusCobain/PersonalCloudLibrarySource/pull/21). The public v0.3.2 extension remains unchanged.

## Implemented

- `PackageDiscoveryPolicy` classifies archives, direct-file types and executables conservatively. ZIP is ambiguous: some emulators load ZIP ROMs directly, so no format triggers unattended extraction or execution.
- `GameLauncherCandidatePolicy` provides read-only executable ranking for a future extracted-package preview. Common installers, dependency setups, crash reporters and uninstallers are flagged as helpers. Multiple similarly plausible launchers remain ambiguous. A suggestion **always requires user confirmation** and cannot execute or publish a play action by itself.
- `ArchiveInspectionPolicy` enforces Windows-aware relative paths, reserved names, duplicate file paths, file-parent collisions, entry/total size limits, excessive expansion limits and rejection of declared links.
- `ZipCentralDirectoryInspector` reads ZIP32 central metadata without relying on `ZipArchiveEntry.ExternalAttributes`, which is absent from the Playnite-supported .NET Framework 4.6.2 API. Encrypted, ZIP64, multi-disk, ambiguous legacy-codepage names, unsupported compression methods, Unix links/special types and inconsistent records are refused. ZIP64 and non-ASCII legacy codepages are **not** supported yet; this is intentional until qualified.
- `ZipPackageStagingExtractor.ExtractApprovedZip` opens a single existing ZIP read-only, verifies central metadata, checks against the pure preflight, and streams into a unique private staging directory inside a pre-existing cache parent. It refuses an existing destination and publishes only after length and central CRC32 checks. It supports cooperative cancellation and reports byte progress.
- Failure/cancellation cleanup removes only files created by this job and then attempts **nonrecursive removal of empty staging directories**. Unknown/symlinked/changed content is not recursively removed; incomplete cleanup is reported for manual inspection instead of risking unrelated files.
- `ZipPackageReviewService.Inspect` now reads an **actual local ZIP without extracting it**, cross-checks strict ZIP32 central metadata, validates the entire entry set through `ArchiveInspectionPolicy`, previews launcher candidates, and classifies single-ROM ZIPs as potential keep-as-archive items (not forced extraction). It binds the read-only review to the file's normalized path and SHA-256 digest. `ExtractAfterExplicitChoice` requires the caller to supply an affirmative extraction choice, match the previously reviewed path, and rehash the ZIP before calling the existing safe staging extractor. Missing consent, changed bytes, invalid review, 7z/RAR masquerades, and occupied destinations fail closed. This is a **service-level guard, not evidence of a shipping Playnite confirmation dialog**. It must not be wired without a real user decision; same-file mutation during the later extractor reopen remains a security-review risk.
- **Playnite read-only inspection entry point:** `PersonalCloudLibrarySource.GameCommands.cs` now offers **Review ZIP Package Contents** on a single selected PCLS game when `ZipGameReviewTargetPolicy` finds a matching local source ZIP or local cached ZIP under the configured cache root. The click handler re-loads the manifest and resolves the current item before inspection, limits the displayed member sample to six paths, reports size and possible launcher/ROM classification, and makes no filesystem change. It does not appear for arbitrary executable files, foreign game IDs, disabled sources or uncached cloud-only ZIPs. Nine new tests check eligibility and stale-source rejection. **This is inspection only:** no extraction button/yes-no consent, transfer queue integration, install state or ownership receipts have been connected yet.
- Deterministic Windows NUnit fixtures cover successful ZIP publish, cancellation, existing target, malicious traversal and reserved paths, ZIP symlink external attributes, case/file-parent collisions, preexisting staging, outside-cache refusal, and corrupted payload CRC.

## Managed ZIP extraction (draft, opt-in)

- The per-game menu now offers **Extract ZIP to Separate Cache Folder** alongside read-only **Review ZIP Package Contents** for a verified local or already-cached ZIP. It re-reads the manifest and source settings, hashes and inspects the ZIP outside the UI thread, and requires an actual Playnite **Yes/No** decision before writing any files. **No means keep the original ZIP**, with no extract or ownership receipt.
- After Yes, `ZipManagedExtractionService` chooses a deterministic hashed **new direct-child folder under the existing cache root**, never a manifest-supplied extraction path. It rejects occupied destinations, existing provenance receipts, an unsafe cache root, and source files nested inside the planned output. It delegates to the pre-existing private-staging ZIP extractor and retains source files.
- A verified, newly committed directory receives a distinct `pcls-zip-<game-id-hash>` inventory receipt (V2) under the plugin's receipt store, separate from ordinary game-install receipts. Receipt recording cannot grant deletion or installed status. If receipt issuance fails **after** extraction, files are preserved and the UI warns that manual attention is required; it never recursively cleans untracked content.
- Extraction and inventory scanning run on a worker thread; a per-game **Cancel ZIP Extraction** action requests cooperative cancellation, and plugin shutdown requests cancellation of outstanding jobs. A cancelled job never adopts or deletes pre-existing files, and the extractor attempts cleanup only of its own private stage.
- **This is not yet the Playnite InstallController's final package install flow.** It does not change the manifest's launch path, mark the game installed, claim ownership of legacy cache content, execute a launcher or installer, or enable recursive uninstall. An extracted directory can be inspected, but proper package-aware Playnite install/action mapping, cleanup/repair UX and native-host cancellation behavior still need completion and acceptance.

## Post-extraction launcher verification (draft, read-only)

- `ZipExtractedLauncherReviewService` reuses the **separate** managed-ZIP V2 inventory receipt and verifies the source identity's deterministic hashed cache folder before considering executable candidates. It compares a fresh SHA-256-based tree inventory with the receipt; added saves or mods, removed/modified executables, absent/mismatched receipts, moved folders, reparse points and unsupported paths all fail closed. This is stricter than merely checking for a matching `.exe`.
- The Playnite per-game context menu offers **Review Extracted ZIP Launchers** only if the matching PCLS game has a recorded extraction in its current cache. The read-only review is dispatched off the UI thread. It shows at most six candidate paths and their classifications and explicitly states that suggestions do **not** approve execution or installation. No launcher is invoked and no Playnite `IsInstalled`, Play action, manifest, ownership policy, or uninstall permission is changed.
- Ten NUnit regressions cover good provenance and installer/helper classification, untracked folders, modified executables, added user saves, deleted files, wrong game identity, invalid roots/IDs, moved extracted folders, cancellation, and absent receipt stores. The separate `ZipManagedExtractionService.ReceiptKeyForGame` identity function is reused by writer and reader.
- The file tree may change after a read-only inventory check; therefore this is **informational evidence only**, not a secure launch authorization. A later real installation controller still needs independently verified launch-path selection, owned destination handling, active-transfer coordination, lifecycle recovery and Windows host acceptance.
- The ZIP approval service now retains an open `FileStream(FileShare.Read)` for the entire approved extraction, *after* verifying the reviewed SHA-256. This blocks ordinary Windows write/delete-sharing replacement between verification and the extractor's read. A Windows regression attempts to open an exclusive writer from the extraction progress callback and requires refusal. This **reduces** the ZIP source replacement race; it is not a complete defense against malicious filesystem actors, directory-level aliasing or kernel-level replacement. The ZIP extractor still independently checks CRC, sizes, paths and central metadata.


## Explicit launcher approval and Playnite mapping (draft)

- **Approve Extracted ZIP Launcher** is a new per-game Playnite context action. The game must already have a recorded managed ZIP extraction. The user is shown up to six non-installer `.exe` candidates one at a time (Yes = select this exact file; No = next; Cancel = stop). No candidate is automatically approved; installers/helpers, scripts and unlisted paths are excluded. Inspection and another complete inventory check run off the UI thread.
- `ZipLauncherApprovalService` stores explicit approval **outside the game cache**, under the plugin data directory. Records are bound to game ID, cache root, deterministic extraction destination, exact relative executable, V2 receipt fingerprint and current source/manifest settings binding. Approval files are create-only; existing approvals cannot be silently overwritten. The saved record is **not authorization on its own**.
- On a successful `GetGames` manifest import, `ApplyExplicitZipLauncherApprovals` finds at most 256 saved approvals, and independently verifies each current source binding, V2 receipt, complete extracted tree inventory, selected non-helper EXE and contained non-reparse filesystem path. **Only** a matching game that was previously uninstalled with no other Play action receives `IsInstalled=true`, an install directory pointing at the managed extracted folder, and one Playnite file Play action. Invalid, missing or stale approvals revert to unchanged manifest-derived metadata; they never cause the whole import to fail or delete a game.
- The explicit approval dialog does not launch any code. The user updates their game library to publish the action; executable invocation happens only if they subsequently choose Play in Playnite. No implicit approval of emulator ZIP contents or installers.
- **Remaining security/acceptance gap:** metadata-based launcher validation happens on library refresh, not on every Play invocation. Filesystem mutations between refresh and a later Play action are not revalidated by this integration. Native installed-host acceptance, durable revoke/repair UX, manifest collisions, performance under very large libraries, ZIP crash recovery and 7z/RAR remain release blockers. Independent review must cover the Playnite SDK behavior and source/file lifetime before claiming production-ready arbitrary ZIP execution.

## Explicit ZIP launcher revocation (draft)

- **Revoke ZIP Launcher Approval** now appears for a PCLS game with a validated approval record under the active cache identity, even if the previously approved source has changed or its extracted inventory no longer matches. A Playnite **Yes/No** warning must be confirmed; No changes nothing.
- `ZipLauncherApprovalService.TryRevoke` removes **only that game's exact plugin-data approval JSON**, after verifying the record version, game ID, cache root, and safe store separation. It does not delete a cache directory, the original ZIP, an extraction inventory receipt, or saves/mods. Invalid/corrupt, linked, absent, foreign-game, foreign-cache and cache-contained approval stores fail closed instead of deleting arbitrary files.
- Another candidate may be approved only through a new explicit selection after revocation. Nine NUnit cases cover consent, stale-source revocation, wrong identity/cache, corrupt record, user files, reapproval, and forbidden store locations.
- On the next **Update Game Library** import, the missing approval causes this ZIP activation overlay to leave the game metadata unchanged. **Playnite may retain previously imported or user-customized actions until refreshed**; the dialog explicitly warns not to run an existing Play action meanwhile. The importer is not a live runtime interception layer. An independently verified per-Play launch guard or Playnite SDK lifecycle integration is still required before treating post-revocation UI behavior as immediately safe.

## Managed ZIP maintenance and legacy uninstall isolation (draft)

- `ZipManagedMaintenanceService` provides **read-only**, cache-identity-bound diagnosis: no extraction, untracked content, missing output, unsafe/mismatched receipt, modified files (including added saves or changed executables), active launcher approval, or exact matching V2 inventory without an active approval. Every outcome sets `CanDeleteUnattended=false`, `CanRepairUnattended=false`, and `CanAuthorizeLegacyUninstall=false`; inventory evidence is **not** a recursive-delete permit.
- A per-game **Review Managed ZIP Maintenance** context action appears if the deterministic managed-ZIP directory or valid ownership receipt exists, including when the directory is missing or contains untracked content. Expensive SHA-256 inventory comparison runs away from the UI thread, with a localized result and warnings to preserve user files. No scan or dialog automatically modifies or repairs files.
- **Critical uninstall safety:** `GetUninstallActions` withholds the legacy manifest-based `PersonalCloudLibraryUninstallController` whenever the game has a managed ZIP footprint. Additionally, the controller now rechecks its managed footprint **at Uninstall execution time** using the supplied plugin receipt store, preventing a stale controller from deleting the original cached ZIP or misapplying a manifest-derived uninstall target after managed extraction begins. Uninstall remains available for unrelated manifest games under its existing safety policy.
- Conservative receipt-footprint detection (`CacheOwnershipReceiptStore.HasReceiptFootprint`) also blocks legacy uninstall when the stored V2 receipt is **corrupt or unreadable** and the extracted directory has been moved. Such a record is treated as an unsafe extraction, not as proof that no package existed. The extra regression test preserves the old cached ZIP even when the receipt JSON has been tampered with.
- Eleven NUnit tests cover clean-but-not-removable inventory, active approvals, modified executables, added saves, removed files, missing/foreign receipts, untracked directories, wrong game identity, cancellation, and refusal of an actual legacy uninstall while preserving the original cached archive and extracted game.
- **Deletion and repair intentionally remain unimplemented:** A future deletion path needs a transaction/recovery record, safe handling of files changed after inventory verification, approval revocation and Playnite library-state reconciliation. Neither a V2 receipt nor a preflight inventory comparison alone can make recursive removal safe against races or user saves.

## Not yet implemented / release blockers

1. Read-only ZIP inspection and an **explicitly confirmed, separate managed extraction** are now available in the draft Playnite game-menu code, but the ZIP result is **not yet connected to package-aware InstallController, Playnite installed-state mapping or launcher configuration**. The standalone output receipt is diagnostic only; neither ZIP ROMs nor installers may be silently extracted or executed.
2. 7z and RAR need an independently reviewed extractor/parser integration with the **same** path, link, decompression, staging and cancellation invariants. Do not treat the ZIP implementation as support for those formats.
3. The ZIP32 parser is intentionally strict: ZIP64, split volumes, encrypted archives, and ambiguous legacy filename encodings fail closed. Unsupported formats must show actionable user guidance.
4. ZIP header CRC checks detect normal accidental corruption, but neither CRC32 nor user-supplied archive metadata is a trusted cryptographic proof of publisher authenticity. No signature or malware scanning is claimed.
5. Concurrent filesystem mutation/reparse-point races still require a Windows-specific adversarial review; the API does not claim handle-pinned filesystem isolation.
6. Source-specific package selection, executable ranking, directory ownership receipts, re-import, and safe uninstall must be integrated with multi-source settings and tested with disposable data.
7. Native Windows Playnite acceptance follows **only after code-complete, integrated CI, and Claude/Grok/Nova review** per [issue #17](https://github.com/KurtusCobain/PersonalCloudLibrarySource/issues/17).

## User safety boundaries

No automatic execution, no source deletion, no destination overwrite, no existing cache adoption, no new recursive deletion permission, no remote account/credential changes. Test fixture teardown only removes its own isolated temporary test directories.

Do **not** advertise all ZIP/7z/RAR installs as working or publish a 1.0 package based on this checkpoint alone.
