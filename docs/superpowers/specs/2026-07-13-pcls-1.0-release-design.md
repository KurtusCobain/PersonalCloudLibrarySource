# PCLS 1.0 Release-Hardening Design

**Date:** 2026-07-13

**Target release:** 1.0.0

**Target branch:** `feature/user-friendly-dashboard-cleanup`

**Status:** Proposed architecture based on the approved risk-first audit

## 1. Purpose

PCLS 1.0 is a release-hardening effort, not a rewrite. It completes or removes every visible but nonfunctional option, makes core GameLibrary behavior dependable in Desktop and Fullscreen, hardens filesystem and transfer lifecycles, makes failures visible, and produces an officially validated package with synchronized metadata.

The design favors targeted extraction from the current implementation. Existing working UI, branding, manifest generation, verification reporting, command policy, and transfer primitives remain unless a finding requires a clearer owner.

## 2. Product boundary

### Desktop 1.0

Desktop provides the complete management experience:

- Settings and provider configuration.
- Guided setup and setup reminders.
- Dashboard, queue, recent activity, reports, diagnostics, and source/cache navigation.
- Startup refresh and optional local manifest generation.
- Game commands in addition to standard GameLibrary controllers.

### Fullscreen 1.0

Fullscreen must reliably support:

- Imported games with stable identity and correct installed state.
- Play actions for launch-ready cached games.
- Install/download actions for eligible remote games.
- Cancellation and useful terminal feedback.
- Uninstall/cache removal with the same safety policy as Desktop.
- Persistent import/source/transfer error or warning feedback available through Playnite-supported mechanisms.

A dedicated Fullscreen dashboard, settings experience, setup wizard, recent-activity screen, or custom game-details window is deferred. Core Fullscreen workflows must not depend on those Desktop-only surfaces.

## 3. Non-goals

- Replacing Playnite's GameLibrary model or controllers.
- A new manifest format without a demonstrated compatibility need.
- A database, web service, account system, or cloud abstraction beyond local paths and rclone.
- Resumable/chunked transfers unless rclone safely provides them without PCLS-specific state.
- A dedicated Fullscreen dashboard or setup wizard.
- Broad visual redesign or new branding.
- Rewriting every large class at once.
- Changing the stable extension ID.

## 4. Architectural principles

1. **One owner per risky decision.** Import errors, path resolution, deletion authorization, queue execution, startup actions, and notifications each have one boundary.
2. **Visible settings are executable contracts.** A setting is wired and tested or removed before 1.0.
3. **Failure is a state, not an empty success.** Provider/import/transfer failures produce stable status and notifications with recovery actions.
4. **Manifest data is untrusted input.** Paths and item fields are validated before filesystem or process use.
5. **The queue owns workers.** UI/controllers enqueue and observe; they do not launch unowned `Task.Run` work.
6. **Shutdown is explicit.** New work stops, queued and active work is cancelled, processes are terminated, waiting is bounded, and partial ownership is deterministic.
7. **Desktop UI is optional to core GameLibrary behavior.** Fullscreen uses metadata, controllers, and Playnite notifications without requiring custom Desktop windows.
8. **Release identity is derived, then frozen.** One validator detects drift; 1.0.0 is applied only after all qualification gates pass.

## 5. Proposed component boundaries

Only components that close a confirmed risk are introduced.

### 5.1 `ManifestLoader`

**Responsibility:** Retrieve manifest text from LocalFile, LocalFolder, or RcloneRemote and return either content plus source description or a typed load failure.

**Dependencies:** Provider settings, local filesystem abstraction, `RcloneManifestReader`, cancellation token, logger.

**Does not own:** JSON parsing, item mapping, Playnite notifications, UI.

**Reason:** `LoadManifestJson` and provider/path decisions currently live inside the 1,162-line plugin class; load failures are flattened by `GetGames`.

### 5.2 `ManifestParserValidator`

**Responsibility:** Deserialize the supported manifest schema, validate version and item invariants, isolate item-level warnings where safe, and return a structured result containing valid items, errors, and warnings.

**Dependencies:** Playnite SDK serialization only where appropriate; no Playnite UI API.

**Validation examples:** Nonempty stable item ID/title, supported source type, relative path rules, duplicate IDs, launch/cache/install consistency, manifest item count consistency, and reasonable limits.

**Reason:** Import and verification must share one definition of validity.

### 5.3 `ManifestItemMapper`

**Responsibility:** Convert a validated item and resolved state into `GameMetadata`, including stable `GameId`, plugin ownership, installed state, install directory, and play action.

**Dependencies:** `LibraryItemStateResolver`, `SourcePathResolver`, plugin ID.

**Does not own:** File copying, notifications, dashboard UI.

**Reason:** Mapping is currently mixed with parsing/path rules and needs a testable Fullscreen-compatible contract.

### 5.4 `SourcePathResolver`

**Responsibility:** Resolve and validate provider-side paths. Local relative paths must remain beneath the configured root; remote paths must be normalized as rclone paths without being treated as local filesystem paths.

**Dependencies:** Provider settings and a small path abstraction.

**Outputs:** Typed success/failure with a redacted display form for messages.

**Reason:** Local, folder, remote, and legacy path logic is duplicated and lexical assumptions are not explicit.

### 5.5 `CachePathResolver`

**Responsibility:** Resolve item cache/install/launch destinations beneath the configured cache, distinguish file and directory packages, and reject roots, empty paths, and prefix collisions.

**Dependencies:** Validated item and settings.

**Does not authorize deletion.** It only resolves destinations.

### 5.6 `LibraryItemStateResolver`

**Responsibility:** Determine remote-only, cached-but-not-launch-ready, installed/launch-ready, source-unavailable, or invalid state from a validated item and resolved paths.

**Dependencies:** Path resolvers and filesystem probes.

**Reason:** Import, command policy, dashboard counts, install availability, and uninstall availability need one state definition.

### 5.7 `SafeCacheDeletionPolicy`

**Responsibility:** Authorize a specific file/directory deletion and return either a canonical target plus ownership category or a refusal reason.

**Required checks:**

- Nonempty, fully normalized path.
- Not a drive/share root and not the cache root itself.
- Inside the cache unless explicit advanced opt-in is enabled.
- No path-prefix collision.
- Target and existing ancestors are not reparse points/junctions/symlinks.
- Deletion kind matches the intended file/directory operation.
- Transfer partial cleanup is limited to a queue-created exact path, not a manifest-controlled arbitrary path.

**Execution:** A small `SafeCacheDeletionService` may perform the already-authorized operation and report outcomes. Policy remains pure and heavily tested.

### 5.8 `TransferQueueService`

**Responsibility:** Own job admission, concurrency, ordering, retries, worker tasks, terminal events, and shutdown state.

**Dependencies:** `TransferExecutionService`, settings snapshot, clock/scheduler abstraction where tests require it.

**Contract:**

- Controllers/commands call `Enqueue` or `Retry`; they do not execute or call `Task.Run`.
- Concurrency limits actual workers, not only state transitions.
- Duplicate active work for one game is rejected or returns the active job.
- Every worker is observed and every exception becomes a failed job.
- Terminal events are emitted once.
- After shutdown begins, no new jobs are accepted.

### 5.9 `TransferExecutionService`

**Responsibility:** Execute one admitted local or rclone job through prepare, connect, transfer, verify, finalize, or terminal failure/cancellation.

**Dependencies:** Local and rclone adapters, cache path resolver, deletion service, cancellation token, progress sink.

**Semantics:**

- Write to a queue-owned partial destination.
- Never overwrite an existing final destination silently.
- Verify before atomic move/finalization.
- Treat verification as mandatory for 1.0; remove the misleading toggle unless a safe alternative is explicitly approved.
- Define incomplete-file retention once. The recommended 1.0 behavior is automatic cleanup of queue-owned partials; remove the toggle if users cannot safely benefit from retained partials.
- Use an rclone connect/start bound and an inactivity timeout reset by output/progress, not a total duration deadline.

### 5.10 `TransferNotificationService`

**Responsibility:** Convert terminal transfer events into settings-aware, localized Playnite notifications and activity records.

**Dependencies:** Playnite notifications API, `DashboardActivityService`, resource provider, navigation actions.

**Rules:** Stable IDs, no duplicates, useful error summary, open-dashboard/report action where applicable, and no UI API access without correct dispatcher semantics.

### 5.11 `ImportNotificationService`

**Responsibility:** Maintain one persistent notification for the current import/source failure and remove it after a successful import.

**Dependencies:** Playnite notifications API, localization, settings/report navigation.

**Reason:** Official maintained library plugins use stable import-error notifications; PCLS currently returns empty data after failure.

### 5.12 `SetupStateService`

**Responsibility:** Evaluate whether setup is valid, new, dismissed, or previously completed and choose none, open Desktop wizard, or show reminder.

**Dependencies:** Existing setup validation and the currently excluded setup launch policy.

**Boundary:** It produces a decision. Desktop navigation/notification code performs the UI action.

### 5.13 `StartupActionService`

**Responsibility:** Run enabled startup actions exactly once after Playnite is ready.

**Ordering:** Validate setup; apply reminder policy; optionally generate a local manifest when eligible; optionally request/perform refresh according to supported Playnite APIs; refresh dashboard state; optionally open the Desktop dashboard.

**Rules:** Disabled/invalid configurations do not start work; duplicate lifecycle calls are idempotent; failures are reported; cancellation is tied to application shutdown.

### 5.14 Existing `SettingsMigrationService`

Retain and strengthen rather than replace.

**Responsibilities:** Sequential schema migrations, safe defaults, idempotence, immutable legacy fixtures, and preservation of user choices.

**Settings lifecycle:**

- `BeginEdit` clones the saved/current object.
- UI edits only the working object.
- `CancelEdit` restores the exact pre-edit snapshot without saving.
- `EndEdit` validates, saves once, and updates runtime services from a snapshot.
- Background services never retain a mutable settings object that the UI is actively editing.

### 5.15 Existing dashboard state services

Retain `DashboardStateStore`, `LibraryStatusService`, `VerificationDashboardStateService`, and `DashboardActivityService`. Connect them through explicit events from import and transfer services. Do not create a second dashboard state model.

View models must have an explicit disposal/unsubscribe path tied to their view/window lifetime.

### 5.16 `ReleaseMetadataValidator`

**Responsibility:** Read, never mutate, the live release surfaces and fail when they disagree.

**Inputs:** Extension manifest version/ID/module/type, assembly version, package/workflow expectations, current README release statement, changelog top release, add-on manifest, installer package entry and URL.

**Outputs:** Human-readable mismatch list and machine failure code.

**Boundary:** Historical specs/plans are excluded from equality checks but may be checked for a visible historical-status label.

## 6. End-to-end data flows

### 6.1 Import

1. `GetGames` snapshots validated settings.
2. `ManifestLoader` retrieves content or returns a typed load failure.
3. `ManifestParserValidator` returns valid items plus errors/warnings.
4. Path resolvers and `LibraryItemStateResolver` compute safe state.
5. `ManifestItemMapper` creates metadata for valid items.
6. Diagnostics/reporting records structured outcomes.
7. `ImportNotificationService` publishes one actionable failure/warning or clears the prior failure on success.
8. Dashboard state is updated on the UI dispatcher only where UI-owned objects are touched.

An operational load failure is never logged as a successful empty library. A genuinely valid empty manifest remains a valid empty library.

### 6.2 Install/download

1. Playnite requests install actions for a PCLS game.
2. State/path services determine eligibility and exact source/destination.
3. Controller enqueues one job and exposes Playnite lifecycle callbacks.
4. Queue admits work under the concurrency limit and runs one observed worker.
5. Execution writes to an owned partial, reports throttled progress, verifies, and finalizes.
6. Terminal state updates Playnite installed state only after launch readiness is confirmed.
7. Notification/activity/dashboard consumers receive one terminal event.

### 6.3 Uninstall/cache removal

1. State resolver identifies the intended file or install directory.
2. `SafeCacheDeletionPolicy` evaluates the target and returns authorization or localized refusal details.
3. The controller optionally asks which safe behavior to use.
4. Deletion service removes only the authorized target.
5. Playnite installed state changes only after deletion succeeds or a verified already-missing state is reconciled.

### 6.4 Shutdown

1. `OnApplicationStopped` marks startup/queue services as stopping.
2. Queue rejects new jobs, cancels queued and active jobs, and terminates rclone through cancellation.
3. A bounded wait occurs without blocking UI-owned work indefinitely.
4. Queue-owned partials follow the approved cleanup policy.
5. Event subscriptions are removed and views/services disposed.
6. No notification/UI callback is attempted after dispatcher/application teardown.

## 7. Error and notification model

Errors are categorized as:

- **Configuration:** Invalid or incomplete settings; action opens settings/setup.
- **Source unavailable:** Missing local/NAS/remote source; persistent notification until recovery.
- **Manifest invalid:** Parse/schema/item errors; report link and concise summary.
- **Transfer failed:** Per-job terminal notification/activity with retry when safe.
- **Verification warning:** Import can continue for isolated item warnings; report and dashboard count.
- **Safety refusal:** Deletion or path resolution is refused; no filesystem mutation occurs.
- **Shutdown cancellation:** Informational activity, not an error unless cleanup/termination fails.

Notification IDs are deterministic by category and, for transfer jobs, by job/game identity. Recovery removes category-level persistent notifications. Message content is localized and avoids exposing secrets; rclone arguments and remote credentials are never included.

## 8. Threading and UI rules

- Playnite SDK and UI objects are assumed not thread-safe unless documented otherwise.
- Queue workers operate on immutable job/settings snapshots and plain data.
- Notifications, dialogs, dashboard state bindings, sidebar properties, and window operations are invoked through `MainView.UIDispatcher` when originating off the UI thread.
- No fire-and-forget task is permitted. The queue observes workers and logs/transitions every exception.
- Progress is throttled/coalesced before dispatch to avoid flooding the UI.
- Events have explicit ownership and unsubscribe/dispose behavior.
- Blocking polling (`Thread.Sleep`) is replaced with signaling/task completion.

## 9. Filesystem safety model

- Treat manifest and setting paths as untrusted until resolved.
- Keep local provider roots, cache roots, source paths, final destinations, and partial destinations as distinct types/results where practical.
- Use separator-aware containment; never plain ambiguous prefix matching.
- Reject rooted item-relative paths where relative is required and reject traversal after normalization.
- Refuse root/cache-root deletion regardless of advanced settings.
- Refuse reparse-point traversal for recursive deletion.
- Advanced outside-cache uninstall never bypasses root/reparse/type checks.
- Do not follow links while computing verification size for an owned directory.
- File and directory operations have separate tested paths.

## 10. Settings and migration decisions

Before 1.0, every setting receives one disposition:

- **Retain and connect:** setup reminders, startup actions, notification preferences.
- **Retain and correct semantics:** rclone timeout, transfer concurrency, uninstall options.
- **Recommended removal:** `VerifyAfterTransfer` because verified finalization is a correctness invariant; `RemoveIncompleteTransferFiles` if PCLS always owns and safely cleans partials. If product review retains either, implementation and tests must match the UI exactly.

Schema migrations are sequential and never infer an old version solely from a renamed CLR class. Legacy fixtures pin the serialized shape from 0.1.1 and 0.2.0. Migration is idempotent and preserves the stable extension data directory.

## 11. Packaging and release metadata

- Continue normal MSBuild build/test outputs.
- Use official Toolbox `pack` for the qualified release artifact; a custom archive may remain only as a developer convenience if its output is compared and never presented as the official qualification path.
- Run Toolbox `verify addon` and `verify installer` against the live YAML files.
- Parse YAML structurally in CI.
- Derive package names from `extension.yaml`, not hard-coded workflow strings.
- Inspect the `.pext` for DLL, extension manifest, icon, localization, and required assets; reject source, PDB (unless separate symbols artifact), temp, or duplicate files.
- Apply the final 1.0.0 version to all live surfaces in one release-preparation commit after other gates pass.
- Compute and publish a SHA-256 checksum for the final artifact.

## 12. Test strategy

### Unit and contract tests

- Manifest loader/parser/validator and item mapping.
- Provider/source/cache path resolution.
- Deletion authorization including reparse points.
- Item-state matrix and play/install/uninstall metadata.
- Sequential settings migration with real legacy fixtures.
- Queue admission, actual concurrency, cancellation, retry, terminal events, and shutdown.
- Notification preference, stable IDs, deduplication, recovery, and actions.
- Startup ordering/idempotence.
- Localization key/reference/literal contract.
- Source-file inclusion and release metadata synchronization.

### Integration tests

- LocalFile and LocalFolder import/install/uninstall.
- Fake and real rclone execution, progress, inactivity, cancellation, retry.
- Fresh-checkout Debug/Release build and package inspection.
- Toolbox pack and both manifest verification commands.

### Manual qualification

- External drive, mapped drive, and UNC/NAS.
- Clean Desktop install and upgrades from 0.1.1/0.2.0.
- Desktop setup/dashboard/activity/queue.
- Fullscreen import/state/play/install/cancel/uninstall/error feedback.
- Branding, screenshots, localization, and documentation links.

## 13. Definition of release readiness

PCLS 1.0 is ready only when:

- The build and full tests pass from a fresh checkout.
- All tracked production/test C# files are compiled or explicitly excluded by an audited rule.
- No visible setting is broken or disconnected.
- Import failures cannot masquerade as an empty successful library.
- Path/deletion and transfer shutdown tests pass.
- Desktop management and Fullscreen core workflows pass their respective matrices.
- Toolbox pack/addon/installer verification and YAML parsing pass.
- Clean install and both upgrade paths pass.
- All live release surfaces agree on 1.0.0 and the final package checksum is recorded.
- PR #9 remains draft until the checklist has no open release gate.
